# The display protocol, `lem.relay.v1`

How `lem-relay` (Lem's side) and a display talk, in practice. The schema,
[`proto/lem/relay/v1/relay.proto`](../proto/lem/relay/v1/relay.proto), is
the reference for every message and field, and its comments say what each
one means. This page is what the schema cannot say: the order things
happen in, what each side can rely on, and where the code is.

Why it is this way is in the ADRs: [0011](adr/0011-a-frame-oriented-protocol.md)
(the principles), [0012](adr/0012-the-relay-frame-model.md) (the frame
model), [0013](adr/0013-icons-and-mouse-input.md) (mouse, time, identity),
[0014](adr/0014-the-display-describes-keys.md) (keys).
[`protocol-notes.md`](protocol-notes.md) is the record of the protocol
this one replaced, `lem-server`'s JSON-RPC.

## Transport

The launcher joins Lem's stdio and the display's with a pipe each way
([ADR 0008](adr/0008-a-launcher-owns-the-processes.md)). Each direction is a
stream of messages, each framed with protobuf's standard length-delimited
format: a varint byte length, then the message.

- Lem sends `ToDisplay`; the display sends `ToEditor`.
- Lem's stdout is the wire and nothing else; its stderr goes to the
  launcher's log (`/tmp/lem-ratatui.log`). The display draws on `/dev/tty`,
  since its stdout is the wire too.
- A stream ending between messages is a hang-up. A stream ending inside
  one is an error: a truncated message cannot be told from a desync.

| | Lisp | Rust |
|---|---|---|
| framing | `relay/protobuf/framing.lisp` | `lem_protocol::v1::{read,write}_delimited` |
| messages | cl-protobufs, generated from the schema | prost, generated by `lem-protocol/build.rs` |

## Every message

Both envelopes carry, before their message:

- `seq`: the sender's count, from 1 per session, in wire order. The relay
  numbers messages under its output lock, so frames from the editor
  thread and answers from the reader thread still number in the order
  they are written.
- `time_us`: when the sender produced it, in microseconds on its own
  monotonic clock since it started. Only compared with the same sender's
  times. The relay's clock is SBCL's `CLOCK_MONOTONIC_COARSE`, a few
  milliseconds' resolution.

With `Hello.session_id`, `(session_id, sender, seq)` names any message. A
reply names its request by `reply_to`, the request's `seq`.

## Starting

```
display                                    relay
   │── Hello (version, session_id, size) ──►│  size and colours taken;
   │                                        │  the editor thread starts
   │◄──────────── Welcome (session_id) ─────│
   │◄──────────── Frame ────────────────────│  the first, unasked
   │◄──────────── Frame ... ────────────────│
```

The editor waits for `Hello` before it starts, because until then it does
not know the screen's size. `Hello` also carries the terminal's own
default colours when the display could find them out (OSC 10/11): Lem
judges light or dark mode by them unless a theme decides. There is no "redraw" step: the first frame
follows on its own. A `Hello` the relay cannot serve (no
`protocol_version`) gets `Exit` with the reason, not silence.

## Frames

A frame is one Lem redraw (`lem-if:update-display`): the ops since the
last one, in order, then state.

- **Ops** follow Lem's own calls: views created, moved, resized, cleared,
  deleted; text put at a cell; a line or the rest of a view cleared; a
  modeline painted whole. The display applies them to a buffer per view.
- **`ViewsStacked`** says which views to show and in what order, bottom
  first. A view not listed is not shown, which is what keeps a virtual
  frame the frame multiplexer switched away from off the screen.
- **Styles** are defined in the first frame that uses each, by id, and
  are stable for the session; 0 is no style. Colours are packed
  `0xRRGGBB`, and an absent colour means the default, not black. Italic,
  strikethrough and dim come from the attribute's property list
  (ADR 0015), and so does the underline style (ADR 0016). That style
  states what Lem wants: a display draws a style its terminal cannot as a
  straight underline.
- **`Defaults`** come in the first frame and whenever a theme changes
  them. The display fills every unset colour with them when compositing,
  so a theme change reaches cells painted before it.
- **`Cursor`** is where Lem's cursor is, within a view, with its shape
  and whether it shows. The display puts the terminal's own cursor there,
  over the cell Lem painted as a cursor.
- **`input_seq`** is the last display message the relay had handed to
  Lem when it closed the frame: what the frame can reflect. It means
  handed to Lem's event queue, not processed by Lem.
- **A put's `width` is authoritative.** The display fits the text to
  exactly that many cells, clipping or padding, so a character whose
  width the two sides disagree on stays inside its run.

**What is never sent** (ADR 0012, `relay/frame.lisp`): a frame that would
change nothing on screen, and a modeline or stacking order identical to
the last one sent. The relay decides this, below the codec, from what it
has already sent: where each view was last blanked from, the cursor, each
view's last modeline, the stacking order and the defaults.
`LEM_RATATUI_DEBUG=1` turns it off, to see everything Lem draws.

## Input

The display reports what happened and the relay turns it into what Lem
consumes:

- **Keys** are described, not named: the character typed, a `NamedKey`,
  or a function key number, with modifiers as reported. The relay maps
  them to Lem's names and applies Lem's shift rules: Alt+Shift+a is
  `M-A`, a space is `Space`. It also turns **C-]** into an abort, which
  interrupts the editor thread instead of queueing, as ncurses and the
  browser client do. Decoding the terminal's bytes correctly is the
  display's job: crossterm's Ctrl+4..7 are sent as the C-\ C-] C-^ C-_
  the terminal meant.
- **Mouse** events come in cells as they happen, with no click count.
  The relay counts clicks: the same button on the same cell within
  `lem-relay/input:*click-interval*` (0.5 s), judged by the display's
  `time_us`, so a slow pipe cannot split a double click.
- **Paste** is text inserted as the major mode pastes; **Resize** makes
  Lem lay out and repaint everything.

## Clipboard

When Lem yanks, the relay sends `ClipboardRequest` and waits 0.1 s for the
`ClipboardReply` that names it by `reply_to`. A late reply to an earlier
request is discarded, not taken for the current one. `text` is absent,
rather than empty, when the display has no clipboard to read. Copying is
a one-way `SetClipboard`.

## Ending

When the editor exits, the relay sends `Exit` and the stream ends. The
reason is empty for a normal exit, or the editor's crash report. The
display restores the terminal and then prints the reason, so it can be
read. If the display hangs up instead, the relay's reader sees the end
of the stream and Lem's process ends with it.

## Where it is tested

- `relay/tests/protobuf.lisp`: the codec and `serve`, in Lisp.
- `lem-protocol` (`src/v1.rs`): framing, in Rust.
- `proto/fixtures/`: golden messages each half decodes from the other.
  - `relay-session.v1.bin`: a real editor session through the relay,
    written by `scripts/capture-relay-v1.lisp`, decoded by
    `lem-protocol/tests/relay_v1_fixture.rs`.
  - `display-inputs.v1.bin`: the display's own conversions, written and
    kept current by `lem-ratatui/src/golden.rs`, decoded by
    `relay/tests/golden.lisp`.

  Each has a text twin (`.txt`) for reviewing a change in a diff.
